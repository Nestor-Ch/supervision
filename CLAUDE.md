# How to use this file
This file has two parts:
- **Part 1 - Dashboard framework** is reusable across projects: architecture, conventions, shared helpers, implementation gotchas, the catalog of page types, and generic deployment rules. A new dashboard copies Part 1 unchanged and writes a fresh Part 2.
- **Part 2 - This project** holds only what is specific to the current dashboard (Supervision survey): its data files and pipeline, its deployment target, and its page list.

When adding a new page, start by identifying which **page type** it is (see "Page types"), then just fill in that type's parameters (dependent variables, disaggregation variables, admin variables, optional extras) in its own short section in Part 2 - the mechanics themselves don't need to be redesigned per page.

# Part 1 - Dashboard framework

## Architecture
These are **Shiny-backed Quarto dashboards** (`format: dashboard` with `server: shiny`), not static self-contained HTML files. This is deliberate: pages need real reactivity (dropdowns that change which variable/graph is shown, cascading admin filters, a reset button) that static crosstalk-linking can't do. Practical implication: a dashboard needs a running R process to view (`quarto preview`, or deployed to a Shiny host) - it can't be shared as a single .html file. `shiny` and `bslib` are already installed in the R environment.

**Static variant (Supervision project, for GitHub Pages).** When the dashboard must be hosted for free with no usage limits, drop `server: shiny` entirely: the whole document becomes static HTML and one Quarto render is all that's needed (no R process at view time; `quarto render index.qmd`, serve/open `index.html`). A document can't mix Shiny and static pages, so *every* page goes static. Pages with no inputs (Type 0, grid pages) keep their R-built htmlwidgets (`plot_ly`/`leaflet` returned directly from an ordinary chunk - no `renderPlotly`/`output$`). Pages with selectors (Type 5) run in the browser with Observable JS (OJS) + Plotly.js, with the data shipped as JSON via `ojs_define()`. The Shiny-specific rules below (server chunk, `renderUI`, `selectize = FALSE`, `keep_selected()`, reset observers, server-side naming suffixes, DT server-side mode) don't apply to static pages. Use `#| include: false` instead of `#| context: setup` for the setup chunk.

All pages live in one `index.qmd`: UI chunks per page, plus (Shiny variant only) one `context: server` chunk holding every page's server logic. Everything shared (data loading, palettes, helpers, constants) lives in the setup chunk and is loaded once.

## Conventions
- **Visual style**: Bootswatch theme set in `_quarto.yml` (Library/Educ4Life: `sandstone`, warm sand palette; Supervision: `cosmo`, blue palette - the whole palette is retinted with the theme: page background, text, bars, ramps, KPI colours, scrollbars and nav popup in `custom.css`, plus the colour constants in the setup chunk and in the OJS grid cell), transparent gridless charts (`paper_bgcolor`/`plot_bgcolor = "rgba(0,0,0,0)"`, `showgrid = FALSE`, `zeroline = FALSE`), the card styling in `custom.css`. Use the existing `index.qmd` as the reference for visual conventions.
- **UI language**: all user-facing text is Ukrainian only - no English glosses or translations next to it (see project memory). That includes DataTables' built-in strings (`dt_language`) and map legend entries.
- **Data problems are flagged, never worked around.** If a label, count, table or export is wrong (a `"None "` option label, a doubled «Вчителі:» prefix, a table older than its DAF, counts that disagree with the raw export), do **not** patch it in the dashboard code - that hides the problem and lets the source stay broken. Run `python check_sheet.py`, report the finding to the user in plain words (what, where, what the correct value is) and ask them to fix it in the data/pipeline/questionnaire, then rebuild. The dashboard reads the data as it is. (Remaining deliberate *presentation* normalisations, listed so they stay conscious: the ".0" is stripped from numeric option labels, and HTML entities are decoded when `openxlsx` reads Ukrainian text from the harmonised KoBo file and from the sheet itself - these are reader quirks, not data errors; `check_sheet.py` still prints a note for the float labels.)
- **Variables are identified by short code** - the `variable_orig` column (e.g. `oblast`, `q1_1`), not the `variable` column, which holds the full Ukrainian question text used for display labels.
- **Server-side naming**: suffix every page-specific input/output id and reactive with that page's number (`dv3`, `map3`, `bar_df_reactive3`, ...) to avoid collisions, since every page's UI and server code lives in the same Shiny app. The reactive/output names listed under each page type are the established convention - reuse them verbatim (with the new page's number) rather than inventing new names. The suffix is an id, not a nav position: a page inserted later can keep a non-sequential suffix (e.g. `1_2`, or `9` placed before `8`) rather than renumbering already-built pages.

## Quarto dashboard implementation gotchas
Hard-won mechanics, bugs and quirks of the dashboard framework itself, not choices specific to a page - assume every new page will hit some of these.

**Layout**
- **Getting real stacked rows inside a `{.tabset}` tab.** Content directly under a tab (`### Огляд`) can default to column orientation for its first heading level, regardless of heading text ("Row" vs "Column") or heading depth; an `orientation="rows"` attribute on the tab heading has been seen silently dropped (never appearing in the rendered HTML). The fix that was confirmed via the generated CSS (`grid-template-rows` only appears with this exact nesting): wrap everything in one no-op `#### Column {width="100%"}` first, then put the real `##### Row {height=...}` sections *one level deeper*.
  - **In practice most pages skip the wrapper and work fine**: `### Огляд {orientation="rows"}` with `#### Row {height=...}` directly underneath, no `#### Column` in between. In the Library dashboard only Page 1 uses the wrapper (every later page uses the simpler form); Educ4Life's pages use the simpler form too. Whether the simple form always works or it's a latent issue nobody has hit wasn't re-verified visually - start with the simple form, and if stacking doesn't render right, fall back to the Column-wrapper version.
- **Prefer pixel heights over percentages** (`height="800px"` not `height="100%"`) for Row/Column sizing inside tabs - percentage heights have repeatedly produced broken/mis-measured layouts in the nested tabset+scrolling-dashboard context; pixel values haven't. (Percentages are fine for a simple top-level page with no tabset - see Type 0.)
- **A fenced div in a page body can't serve as a page-wide banner when the page has a sidebar.** Placed before `## {.sidebar}` it breaks the sidebar layout outright; placed after, it's silently absorbed into the sidebar's content region (bslib's sidebar content boundary runs until the next `##` heading). Inject such elements with a DOM pass instead - see "Nav-tab icons".
- **Headings inside page/tab content are always layout boundaries.** Quarto dashboards have no "just prose" heading tier: every heading, at every level, is a page/row/column/tab boundary. See the include-file gotchas below for how this bites.

**Text and included files**
- **`shiny::includeMarkdown()` isn't usable in this environment** - it hard-requires the `markdown` R package (`packageVersion("markdown")` inside `htmltools::includeMarkdown()`), which isn't installed, so calling it fails the whole render (`there is no package called 'markdown'`), not just that one chunk. For a pure-text tab/card, use Quarto's own `{{< include path.md >}}` shortcode directly in the markdown body instead - no R package needed, and it renders through the same Pandoc pipeline as the rest of the page (consistent styling, not a separately-styled htmlwidget).
- **A heading inside an included `.md` file can silently wreck the surrounding layout.** An `{{< include >}}`'d file's `##`/`###` headings get spliced into the document tree at render time, so if the include sits inside a `### SomeTab` (where `##`/`###` are already claimed by the tab structure) and the included file also uses `##` for its own section titles, each one is misread as a new Row/Column boundary. Symptom (no error): the whole tabset collapses into generic "Tab 1"/"Tab 2" labels with extra un-tabbed stacked rows below it. Fix: never use real markdown headings inside an included text file that lives in a dashboard tab - use bold text (`**Section**`) on its own line, and let paragraph breaks do the rest.
- **An `{{< include >}}`'d file that's completely empty breaks that tab's own label** - Quarto falls back to a generic "Tab N" placeholder instead of the real `### <TabName>` text when the tab body resolves to zero rendered content. A one-line placeholder (e.g. `_Матеріал буде додано._`) keeps the real label while the file is still a work in progress.

**Inputs and reactivity**
- **Dynamically-regenerated dropdowns need `selectize = FALSE`.** Any `selectInput()` rebuilt via `renderUI`/`uiOutput` (its choices depend on another input, like `admin1_ui`/`admin2_ui`/`dv_option_ui`) doesn't reliably sync its selectize-enhanced `<option>`s with the server-computed choices - the server computes the right values, but the widget shows only its placeholder. Plain `<select>` (`selectize = FALSE`) avoids the bug entirely. Static, never-regenerated inputs (`dv`, `disagg_var`, `stat`) don't need this.
- **Rebuilt dropdowns must restore their own selection.** A `renderUI` dropdown re-renders whenever anything it reads changes (e.g. the dependent variable), and a `selectInput()` without `selected` snaps back to its first choice - for the admin dropdowns that silently drops the user out of an oblast/hromada drill-down every time they change the variable. Pass `selected = keep_selected(isolate(input$<id>), <valid choices>)` (`keep_selected()` is a setup-chunk helper: keeps the current pick if it's still among the valid choices, else `""`). The `isolate()` matters: without it the dropdown would depend on its own value. If the new variable has no data for the selected oblast/hromada, it falls back to "all" by design. The map-option dropdown (`dv_option<N>`) re-renders on every admin 1 change too (its choices differ between oblast and hromada level), so it uses a per-page, per-session `keep_option<N> <- make_option_keeper()` (defined just above its `renderUI`): it keeps the user's option across admin changes when it's still offered, but resets to the first option when the *dependent variable* changes - a new variable should start on its first option even if it shares an answer label ("так") with the old one.
- **`if (cond) {A} else {B} -> p` does NOT assign the whole if/else to `p`.** R's right-assign `->` only binds to the immediately preceding branch (the `else` block) - the `if` branch's value is silently discarded, and if the `if` branch runs, `p` is left unassigned (or resolves to some unrelated same-named object, e.g. a function, producing a confusing error like "no applicable method ... applied to an object of class 'function'"). Always use left-assign: `p <- if (cond) {A} else {B}`, or assign inside each branch. Caught in a Type 2 `bar<N>` output, where the disaggregated (`if`) branch silently failed while the `else` branch worked - a reminder to click through every selector during testing, not just the ones that render first.

**Rendering, preview and debugging**
- **`quarto preview` can silently serve a stale build.** If a code change doesn't seem to take effect, don't trust it - kill the R/quarto process and start a fresh `quarto preview` on a new port before concluding something else is wrong.
- **Preview/automation on this machine**: `quarto preview` doesn't hot-reload edits to a Shiny dashboard reliably - after every edit, stop the preview and start a fresh one on a **new port**, otherwise screenshots show the old build. Stop it by the process listening on its port (`Get-NetTCPConnection -LocalPort <p>` -> owning Rscript + its parent `cmd.exe`), never by image name (`taskkill /IM R.exe`) - that would kill the user's own R sessions. A plain headless-browser `--screenshot` captures **before** Shiny's websocket outputs render (charts blank); drive the browser over the DevTools protocol instead and wait ~25 s before `Page.captureScreenshot` (a ~40-line Node script with Edge's `--remote-debugging-port` does it; Node's built-in `WebSocket`/`fetch` are enough, no packages).
- **Never compute large tables in a static (non-reactive) chunk.** A plain `{r}` chunk executes unconditionally at *every* `quarto render`/app startup, and DT's default client-side mode serializes the *entire* dataset as inline JSON into the page. With six pages each doing this against a ~4,200-row respondent file, render time was ~3m16s, almost all of it Pandoc parsing six multi-MB single-line JSON blobs (disabling them: ~33s). Every table is a `renderDT`/`DTOutput` pair (`output$raw_data<N> <- renderDT({...})` in `context: server`, `DTOutput("raw_data<N>")` in the UI), so it only computes when a live session opens that tab. (A scalar like a value box is fine in a static chunk - see Type 0.)
- **`addLegend(..., labFormat = labFormat())` fails at runtime with "could not find function 'labFormat'".** The leaflet function is `labelFormat()` (with "el") - `labFormat` is only `addLegend()`'s *parameter* name. It crept into two different pages' maps, each time in the *drilled-down* (oblast-selected) branch - the one least likely to be exercised by a quick default-view test. The failure is silent in the browser (no `.shiny-output-error` banner; the leaflet div just stays empty, `innerHTML.length == 0`) and only shows in the R/quarto console. When a map renders blank with no visible error, check the R console log first, and test the drilled-down branch specifically. (Maps now use manual legends via `map_scale()`, so `labelFormat()` isn't needed at all - see "Maps".)
- **`readxl::read_excel()` vs `openxlsx::read.xlsx()`**: the setup chunk loads `openxlsx` but not `readxl`, so a bare `read_excel()` call fails with "could not find function" rather than a clearer missing-package error. Use `read.xlsx()`, or call `readxl::read_excel()` fully qualified (as the raw-data loader does).

**DataTables (DT)**
- **Every `DT::datatable()` inside a dashboard card needs `bPaginate = TRUE` set explicitly** in its own `options` list. Quarto dashboards globally force `bPaginate = FALSE` and truncate `dom` down to `"t"` on every DT table in a card (a documented `DT.options` override meant to make tables fill-scroll instead of paginate) - this silently overrides your own `pageLength`/`dom`. Symptom when missed: the *entire* dataset gets dumped unpaginated into one giant table, of which the viewport shows only the first row - looks like "the table is too small," but the cause is pagination being off.
- **Download/export buttons silently don't appear if `dom` doesn't include `"B"`.** `dom` is a DataTables layout string - each letter is a placeholder for one UI piece, in render order: `l` length menu, `f` search box, `t` the table, `i` info text, `p` pagination, `B` the Buttons toolbar. Adding `extensions = 'Buttons'`/`buttons = ...` without `B` in `dom` configures the buttons correctly but gives them nowhere to render - no error anywhere. If buttons aren't showing, check `dom` first.
- **Standard options for every table**: `extensions = 'Buttons'` and `options = list(pageLength = ..., dom = "Bltip", lengthMenu = dt_length_menu, language = dt_language, bPaginate = TRUE, buttons = c('copy', 'csv', 'excel', 'pdf', 'print'))`, plus `filter = "top"` (a per-column filter row) on raw-data-style tables. `dom = "Bltip"` = buttons/length menu/table/info/pagination, no global search box. `dt_length_menu` and `dt_language` (Ukrainian strings for the length menu, info text, pagination and Copy/Print buttons - DataTables' defaults are English) are shared constants in the setup chunk. Page sizes: 25 for raw-data tables, 10 for a chart's small "Дані" tab.
- **Length menu**: `dt_length_menu` = 10/25/50/100/Усі unless the user states otherwise (this is only relevant when working with small datasets).
- **DT's unnamed `colnames` argument must have exactly `ncol(df)` entries, including hidden helper columns.** If a table has a hidden column (e.g. a `significant` flag used only by `formatStyle`, hidden via `columnDefs = list(list(visible = FALSE, targets = ncol(df) - 1))`) and `colnames` labels only the *visible* columns, DT still assigns labels positionally across *all* columns - every header silently shifts one column left of its data, no error. Always size `colnames` to the full `ncol(df)`, with a throwaway label for any hidden column.
- **Tables run with `serverSide = TRUE`** (part of Quarto dashboard's fill-scroll `DT.options` default) - the browser only holds the *currently visible page* of rows. Invisible to users, but a trap when inspecting a table programmatically (browser automation, `$(table).DataTable()...` console snippets): `dt.rows().data()` **and even `dt.rows({page: 'all'}).data()`** return only that page (`{page: 'all'}` overrides a search filter, not server-side pagination). To read every row: `dt.page.len(-1).draw('page')`, wait for the round-trip, then `dt.rows({page: 'current'}).data()`. Every "missing row" false positive in a data audit of the Library dashboard traced back to this.
- **Default DataTables scrollbars look out of place** against the theme - fixed globally in `custom.css` (thin, theme-colored scrollbar rules for `.card-body`/`.dataTables_wrapper`/`.dataTables_scrollBody`), so new pages get this automatically.

## Data contract (DAF pipeline outputs)
Both projects so far feed the dashboard from the same pipeline: `generate_dashboard.py` turns a DAF (data analysis framework) spreadsheet plus the cleaned respondent data into long-format parquet tables. Columns as the framework uses them:

| Framework concept | Column(s) | Notes |
|---|---|---|
| DAF row id | `ID` | The source DAF row's id, carried through unchanged. Useful for selecting or excluding blocks of rows (see "Subset pages" under Type 3) and for per-chart special cases. |
| Dependent variable | `variable_orig` (short code) / `variable` (Ukrainian label) | One row per (ID, variable, admin level, admin value, disaggregation, option) combo |
| Dependent variable option | `option` (label) / `option_orig` (short code) | The answer choice; `perc` is its share for that row's filter combo. Numeric (Type 2/3) rows have no `option` (NA) |
| Admin level / value | `admin` / `admin_category` | `admin == "Overall"` is the unfiltered state. Other levels are project-specific (Library: `oblast`, `hromadaId`; Educ4Life: `school_id`) - see Part 2 |
| Disaggregation variable | `disaggregations_1` (label) / `disaggregations_1_orig` (short code) | `"Overall"` when unset - check the project's exact spelling (Library has a leading space: `" Overall"`) |
| Disaggregation category | `disaggregations_category_1` | The category within the chosen disaggregation variable |
| Share | `perc` (0-1) | Categorical rows. `general_count`/`general_count_uw`/`full_count` are **not** per-option counts - they're the same base N repeated across every option row of one (variable, admin, disaggregation) combo. The per-option respondent count is `response_count = round(perc * general_count)`, precomputed once in setup |
| Statistics | `mean`/`median`/`min`/`max` | Numeric rows |
| Chart title | `title` | Optional, only if the project's pipeline adds it (Library does - see "Dynamic chart titles") |

Numeric variables come with a **second, per-distinct-value frequency table** (`agg_num`): `option`/`option_orig` = the raw numeric answer, `perc` = its share for the row's filter combo. It drives histograms only.

**A dependent variable can be legitimately absent from the aggregated data for two different reasons - don't assume either without checking:**
- It's genuinely missing because it's a free-text field the DAF pipeline can't summarize (only `mean`/`numeric`/`select_one`/`select_multiple`/`freq` are supported) - confirm by checking the KoBo tool file for the field's type.
- It's present in the data but deliberately left off a page's dependent-variable list by design (e.g. an ordinal rating on a page of continuous counts) - confirm by checking whether it actually appears in `variable_orig` before concluding it's missing.

**Duplicate rows for the same (variable, admin, disaggregation) combo** silently break charts ("they collapse in the visualisations and cause weird percentages"). They appear when a DAF carries two analyses of the same variable (e.g. a full-sample and a subset copy - see "Subset pages" under Type 3). Separate them by `ID` *before* any dedup step: a plain ungrouped `distinct()` keeps whichever side sorts first and silently discards the other.

## Raw data card (Types 0/1/2)
Each page has a hidden "Сирі дані" tab showing that page's respondent-level columns under readable (Ukrainian) headers. Type 3 replaces it with a school-breakdown table.

1. Load once in setup: the respondent-level file whose **column headers are the full question labels** (`raw_clean`), and the KoBo tool's survey sheet as `dictionary` (short code `name` -> `label`).
2. Per page: `current_view<N> <- c(<id column>, "name", ...)` - the short codes the page touches plus an id column. Include every variable the page touches, even non-chartable ones (free-text fields) - they're useful context in the raw table.
3. `clean_labels<N> <- dictionary %>% filter(name %in% current_view<N>) %>% pull(label)` - resolve short codes to column headers.
4. `raw_clean %>% select(c(<id column>, clean_labels<N>))`, with the matching `DT::formatStyle(columns = seq_along(c(<id column>, clean_labels<N>)), ...)` (by position - see the line-ending gotcha below). An id column isn't a KoBo question, so step 3 silently drops it - add it back here. Don't prepend it to `clean_labels<N>` instead: that would shift every index-based label patch (below) by one.

Gotchas:
- **Free-text "other, please specify" fields** (`*_other`) are often missing from the dictionary - patch the label by index, e.g. `clean_labels<N>[7] <- "Якщо «інше», вкажіть (q2_4_other)"`. The index follows the dictionary's row order, not `current_view`'s - compute it and check.
- **Multi-line labels can differ in line endings** - and the difference depends on the machine: the respondent file's headers carry `
` while the KoBo label cell may come back as `
` or `
` depending on the OS/package version reading it. A mismatch makes `select()` silently match nothing (the column goes missing, or the DT widget renders empty) - or, as happened on the shinyapps.io (Linux) deploy of Library Page 6, `DT::formatStyle()` fails with "Can't select columns that don't exist" and the whole raw-data table is blank. Two rules, both in the setup chunk and both needed: (1) normalize **both sides** with the same helper - `norm_newlines()` applied to `colnames(raw_clean)` and to `dictionary$label` - never just one; (2) style columns **by position**, not by name: `DT::formatStyle(columns = seq_along(c(<id column>, clean_labels<N>)), ...)`, so styling can't depend on how a name with a line break survives DT's own processing (verified to produce identical output to name-based styling).
- **PII columns** must never be selected - list them per project in Part 2.

Build it as `output$raw_data<N> <- renderDT({...})` + `DTOutput("raw_data<N>")` with the standard DT options (`pageLength = 25`, `filter = "top"`). It has no selector dependencies; it's a render function only so it computes on first view instead of at startup (see the static-chunk gotcha).

## Shared chart helpers (setup chunk)
Reuse these rather than styling charts per page.
- **`chart_title(text)`** - shared plotly title styling (font, color `#4a3018`, left-aligned) plus wrapping: plotly titles render as SVG text and don't auto-wrap, so `chart_title()` inserts `<br>`s via `wrap_label()` at **120 characters** (~850 px at this font size: fits a chart on a 1280 px laptop window - a wider limit overran the right edge, and plotly can't re-wrap responsively; real titles run up to ~290 characters, so ~2-3% still wrap to 3 lines). The title's top is pinned to the chart's top edge (`y = 1, yanchor = "top", yref = "container"`) with `pad = list(t = 26)` and `automargin = TRUE` growing the top margin to fit it - the padding matters: with a small pad (8) the title's text box measured 5 px *above* the chart container, so the top few pixels of the first line were clipped right under the tab selectors; at 26 it sits 13 px inside (measure `.gtitle` bbox top vs the chart's top, in CSS px, if you change fonts or sizes): with plotly's default (title anchored by its bottom, fixed margin) extra lines grew upward out of the chart and the first line of a 3-line title was cut off or ran into the plot.
- **`wrap_label(x, width = 28)`** - `<br>`-wrapping for long category labels on bar-chart axes.
- **`hbar(df, color, value_col, tickformat, title)`** - single-series horizontal bar chart over `option`, sorted by value. **`hbar_grouped(df, value_col, tickformat, title)`** - one bar group per disaggregation category, one color per option (legend). Both default to `perc`/`.0%`; pass `value_col = "response_count", tickformat = ",d"` for counts.
- **Bar value labels / number format**: every bar chart shows its value at the end of each bar and in the hover box, via `bar_labels(p, tickformat)`, in the same d3 format as the x axis. `hbar()`/`hbar_grouped()` apply it themselves (`.0%` percentages, `,d` counts); hand-built statistic bars call `bar_labels(stat_tickformat)` and set `xaxis = list(tickformat = stat_tickformat, ...)` (`",.2~f"` - at most 2 decimals, trailing zeros trimmed), so raw statistics like `6576.833333` never show unrounded. Keep `margin = list(..., r = 50)` so the outside labels aren't cut off.
- **`bar_xaxis(tickformat)`** - the x axis used by `hbar()`/`hbar_grouped()`: percentage charts are fixed to a 0-100% range (standard across the dashboard); counts and statistics keep plotly's automatic range.
- **`hist_title(title)`** - strips the "Обрана статистика: ..." clause from a title, for histograms that always show the full distribution regardless of the selected statistic.
- **Donut charts** - plain `plot_ly(..., type = "pie", hole = 0.55)` on a frequency count, with `textinfo = "label+percent"` and `textposition = "outside"`: plotly's default (`"auto"`) puts labels inside the ring when they fit, which crowds a donut with only 2-3 slices; `"outside"` pushes them out with leader lines. No shared helper - each is built inline in its own `renderPlotly`.
- **Correlation heatmap color scale**: `plot_ly(..., type = "heatmap", colorscale = "RdBu", reversescale = TRUE, zmin = -1, zmax = 1)` - plotly's built-in diverging scale, reversed so positive = warm/red and negative = cool/blue (matching the warm palette), with a fixed -1..1 domain so a color always means the same correlation strength on every page and view. No helper needed - the fixed domain means there's no per-view range to compute.

## Maps
- **Geometry, oblast level**: a cached `data/oblast_geo.geojson` (Natural Earth admin-1 polygons, columns `name` + geometry), read with `sf::st_read()`. **Never call `rnaturalearth` at runtime** - it breaks the shinyapps.io build (see "Deployment"); the rebuild recipe is a comment next to the `st_read()` in the setup chunk. Natural Earth files Crimea and Sevastopol under `admin == "Russia"` (de facto control), so the cache is built as Ukraine's states **plus** those two polygons pulled from the unfiltered dataset by `name %in% c("Crimea", "Sevastopol")` - the map shows Ukraine's internationally recognized territory. They render as no-data when the survey has no responses there.
- **Geometry, lower levels** are project-specific (Library's hromada file - see Part 2).
- **No basemap tiles** (`addTiles()`/`addProviderTiles()`) - polygons only, transparent background. Two reasons: a tile layer breaks the transparent gridless look; and most free hosted tile providers (CartoDB included) now watermark unauthenticated tiles "for evaluation purposes only".
- **leaflet's bundled CSS paints an opaque grey background even with no tiles** (`.leaflet-container { background: #ddd }`), injected into `<head>` after `custom.css` with the same specificity, so it wins. Fixed in `custom.css` with `.leaflet-container { background: transparent !important; }`.
- **Scroll-wheel zoom is disabled** (`leafletOptions(scrollWheelZoom = FALSE)`) so ordinary page scrolling over a map doesn't zoom it; pinch, drag and the zoom buttons still work.
- **Map title**: leaflet has no title slot, so a map's title is a `textOutput("map_title<N>")` wrapped in `div(class = "map-title", ...)` directly above its `leafletOutput`, styled by `custom.css`'s `.map-title` rule to match `chart_title()`.
- **Color scale / legend - `map_scale(values, mode, digits)`** (every map): returns per-geography fill colors (`sc$colors`, passed to `addPolygons(fillColor = ...)`) plus manual legend entries (`sc$legend_colors`/`sc$legend_labels`, passed to `addLegend(colors =, labels =)`) - not `colorNumeric()`/`colorBin()`/`pal =`, so legends stay stable instead of restretching to each view's min/max. Modes:
  - `"perc"` (percentage maps): fixed bins 1-19 / 20-39 / 40-59 / 60-79 / 80-100 %, plus a separate pale blue-grey (`map_zero_color`) for an exact 0, so a confirmed zero is distinguishable from both low values and no-data.
  - `"capped"` (statistics, and counts): 5 equal-width bins from 0 to the **95th percentile of the values currently on the map** (recomputed per variable/statistic/drill-down); everything above P95 falls into a last, open-ended `≥ X` bin, so outliers can't stretch the scale. No special zero color. `digits = 2` for statistics (legend labels and tooltips show 2 decimals); counts use integer edges, collapsing to fewer bins when the range is tiny (e.g. counts of only 0/1).
  - `"share"` (an overview map of each region's share of *all* respondents): same zero color and ramp as `"perc"`, but finer bins 0 / 1-5 / 6-10 / 11-15 / 16-20 / >20 %, upper edges inclusive - shares like these are small (Library: median ~7.5%, max ~22%), so the `"perc"` bins would paint almost every region the same color.
  - NA (no data) is always the dark grey `map_na_color`, with a "немає даних" legend entry only when an NA is present.
- **Overview-map scale**: different dashboards need different modes on the overview (Type 0) page - some show each region's share of respondents (`"share"`), others respondent counts (`"capped"`). Ask the user which one the overview page should show before implementing anything.

## Nav-tab icons
Dashboard-wide: every top-level page tab's text label is swapped for a Bootstrap Icon glyph, with the original text moved into a hidden label shown on hover, plus a plain-text page-title banner inserted at the top of each page's content (since the tab no longer shows the name). Bootstrap Icons are already bundled by the Quarto dashboard format (no separate stylesheet needed).

**Why a DOM pass after load, not markup in the `.qmd`.** Two direct approaches failed silently: raw HTML/an icon tag in a page's `#` heading (the nav generator stringifies heading content to plain text, discarding markup), and a `::: {.page-title} :::` fenced div for the banner (breaks or is absorbed by the sidebar - see the layout gotchas). So a script runs once on `DOMContentLoaded`: it finds every `a.nav-link`, looks its exact trimmed text up in a `NAV_ICONS` map, and - only for matches - replaces its `innerHTML` with `<i class="bi <glyph> nav-icon">` plus `<span class="nav-label">` holding the original text, and inserts a `.page-title` div as the first child of that tab's page container (`document.getElementById(pageId)`, from the link's `href`).

**Where the script lives**: a separate `nav-icons.html` next to `index.qmd`, wired in via `_quarto.yml`'s `include-after-body: nav-icons.html`, and explicitly *not* pasted inline, because `include-after-body` is the Quarto-native way to inject a fixed post-body snippet without it becoming part of any one page's content.

**Keyed by exact page title text - a rename breaks the match silently.** `NAV_ICONS`' keys must equal each page's `#` heading text exactly. If a heading changes and `NAV_ICONS` isn't updated, that tab silently falls back to its plain-text label (`if (!icon) return` - nothing errors). Keep the `#` heading, the `NAV_ICONS` key and Part 2's page list in sync on any rename. Inner sub-tabs (Огляд/Сирі дані/...) are never in the map, so they're skipped the same way.

**Icon choice**: each page gets its own thematically fitting Bootstrap Icon (`bi-...`); don't reuse another page's glyph. The current project's map is in Part 2.

**Styling** (`custom.css`): `.nav-icon` sizes the glyph; `.nav-label` is `display: none` by default and shown as a small absolutely-positioned popup on `a.nav-link:hover` (`a.nav-link` needs `position: relative` so the popup anchors to it); `.page-title` is a plain banner in the text color `#4a3018`.

## Page types
Every page's selectors, reset behavior and chart mechanics come from one of the reusable types below. Pick a type, then write that page's own section (Part 2) as just its parameters. Don't redesign the mechanics per page.

| Type | For | Selectors | Graphs |
|---|---|---|---|
| 0 - Fixed overview | A summary page, no dropdowns | none | pick from: overview map, bar charts, donuts, value box; optional raw-data card |
| 1 - Categorical | Variables with discrete answer options | variable, option, admin 1/2, disaggregation | map, bar chart |
| 2 - Numeric with geography | Continuous variables, oblast/hromada dimension | variable, statistic, admin 1/2, disaggregation | map, bar chart, histogram |
| 3 - Numeric, no geography, correlations | Continuous scale scores, no admin dimension | variable, statistic, disaggregation | bar chart, histogram, correlation matrix, findings text, school breakdown |
| 4 - Static text | Analyst-written prose | none | none (included `.md` files) |
| 5 - Grid with a breakdown selector (static) | Several variables of one theme shown together, no variable picker. Two variants: **standard** (one respondent population) and **two-group comparison** (every table split by respondent group) | breakdown, percentages/counts | one card per variable; chart type depends on the breakdown (and, in the comparison variant, on the group) |

### Mechanics shared by every selector page (Types 1, 2, 3)
- **Disaggregation variable**: dropdown for which variable to disaggregate the bar chart by. Unset ("Немає") = Overall.
- **Dropdown scoping**: every dropdown (option/statistic aside) only offers choices that actually have data for the currently selected dependent variable (and, for admin 2, the selected admin 1) - never let the user pick a combination that renders an empty chart.
- **Reset button**: an `actionButton` that resets every selector on the page (dependent variable, option/statistic, admin 1/2, disaggregation, any optional toggle) to its default via `updateSelectInput`/`updateRadioButtons` in one `observeEvent`.
- **Chart + underlying-numbers tabset** (optional extra): to let the user flip from a chart to the exact numbers behind it, wrap the chart and a small `DTOutput()` in a nested `##### {.tabset}` one level under the chart's Row. The tabset heading's own text is never displayed - only its children's `#| title:` values become tab labels, so give the chart's chunk the real title (e.g. "Розподіл за варіантами відповіді") and the table's chunk `"Дані"`. Build both from one shared `reactive()` (`bar_df_reactive<N>()`) so they can never disagree. The table (`bar<N>_data`) gets the standard DT options with `pageLength = 10`.
- **Dynamic chart titles**: every map/bar/histogram carries a title describing exactly what's selected (variable + option/statistic + admin scope, or + disaggregation), instead of a fixed `#| title:` card header, passed through `chart_title()` (or the `.map-title` div for maps). Two ways to build the text, depending on the pipeline:
  - **Precomputed `title` column** (Types 1/2 in the Library project): built per row in the pipeline's post-processing step (Library: `data/preprocessing_stage2.R`, one `case_when()` branch per admin-level × option-vs-statistic × disaggregated-or-not combo - 9 branches, `.default = NA_character_` should never fire), with two literal placeholders for what a single row can't know: `__HROMADA__` (the readable hromada name - not joined on until the setup chunk) and `__STAT__` (which statistic the viewer picked - Type 2 rows carry all four as columns). `complete_title(title_text, admin_2, stat_label)` fills both reactively with `gsub()`. Every page then follows the same two-reactive shape:
    - `map_title<N>()`: always the "one specific option/statistic" row's title for the current admin scope (`bar_scope<N>()`) - Type 1 filters by `option == input$dv_option<N>`; Type 2 has no option filter (the row is already unique per admin scope) and completes `__STAT__` from `input$stat<N>`.
    - `bar_title<N>()`: when `disagg_active<N>()`, the "Обрана дизагрегація" row's title from `bar_df_reactive<N>()` (constant across that pull). Otherwise: Type 2's single bar shows the same value as the map, so it reuses `map_title<N>()`; Type 1's bar shows the *full* distribution across every option, so reusing the map's "Обрана опція: X" title would misleadingly claim it's filtered to one option - it's built directly as `{variable label}` + an admin-scope suffix (`", Обрана область: ..."` / `", Обрана громада: ..."` / none for Overall).
    - Histograms (`hist<N>`) have no title data of their own (`agg_num` has no `title` column) - they reuse `map_title<N>()` through `hist_title()`.
  - **Built directly in R** when the data has no `title` column (Type 3 in Educ4Life - its pipeline calls `generate_dashboard.py` directly, with no post-processing step): build titles from `variable`/`disaggregations_category_1`, the same way Type 1's undisaggregated bar title is built. No `complete_title()`/placeholders.

### Mechanics for geographic pages (Types 1, 2)
- **Administrative category 1**: dropdown for the top admin level (oblast).
- **Administrative category 2**: dropdown for the lower admin level (hromada), cascading from category 1 (only offers units inside the selected oblast). Value = the raw code (used for filtering), label = the readable name.
- **Map drill-down**: picking an admin 1 switches the map from the national oblast choropleth to that oblast's hromada choropleth; picking an admin 2 additionally highlights that hromada with a thicker/darker border. Both selectors also filter the bar chart to that admin scope (`bar_scope<N>()`: "Overall" / "oblast" / "hromadaId" - three-way, since "oblast only" and "oblast + hromada" are different bar-chart scopes even though the map only has two states).
- Admin column semantics, geometry files and code formats are project-specific - see Part 2.

### Type 0 - Fixed overview, no selectors
A summary page with **no selectors and no reset button** - every output is computed once per session rather than driven by `input$...`. Usually placed first. The page picks from these building blocks:
- **Overview map** of one geographic variable, built from that variable's own options: the option *is* the map geography (option -> polygon, value -> fill color; e.g. Library's `oblast` variable, whose options are oblast names). No option selector, since there's no per-admin cross-tab to select against. Scale per "Maps": shares via `"share"` or counts via `"capped"` - ask the user which. Alternatively, a respondent-count map computed from respondent-level data (Educ4Life: `clean_scores$Область`, from its school dictionary).
- **Bar charts**, one always-visible card per fixed variable (`hbar()`, no filtering).
- **Donut charts** (see "Shared chart helpers").
- **Value box**: Quarto's native `#| content: valuebox` chunk metadata (not a Shiny `render*`/`*Output` pair), e.g. `list(icon = "building", color = "primary", value = n_distinct(...))`. Computed once at build time - fine for a scalar derived from data already loaded in setup.
- **Raw-data card** (optional): a `{.tabset}` with "Огляд" and "Сирі дані" tabs; the raw-data table still follows the reactive `raw_data<N>` pattern (see "Raw data card") even though nothing else on the page is reactive.

**Layout examples.**
- Library Page 1: an `{.tabset}` (Огляд / Сирі дані); Огляд stacks the map row and a row of two bar charts, using the `#### Column {width="100%"}` wrapper (see the layout gotcha).
- Educ4Life Page 0: no tabset, three stacked `## Row`s - a 40%-height map row; a 30% row split `#### Column {width="25%"}` value box / `{width="75%"}` participation donut; a 30% row split 50/50 between a gender donut and a reading-time donut. (Percentage heights are fine here because there's no nested tabset.)

### Grid pages (lessons from Supervision Page 0)
Not a numbered page type: a Type 0-style page with no selectors (no sidebar, no tabset, no reset button) that lays all of its variables out at once, each element sized by what its chart naturally needs. The first one was the Supervision survey's page 0 ("Загальне"); the rules below apply to any such page, including the Type 5 pages (which have selectors, but share the card sizing and chart-card rules). Implemented as three stacked `## Row {height=...px}` (pixel heights), outputs as `renderPlotly`/`renderLeaflet` in the server chunk, suffix `0`.

**Element sizing**: KPI strip on top (smallest) -> the map (largest, ~55% of the main row's width, ~600px tall) with two small charts stacked beside it -> a bottom row of the tallest bar charts. A bar chart needs roughly 25-30 px per bar plus ~100 px for title and axis (13 bars -> ~520px; 4 bars -> ~250px). Check the layout at both 1400 px and 1024 px widths.

**KPI value boxes**
- `#| content: valuebox` with `list(icon, color, value)` in the chunk's last expression. `value` must be a **plain character string**: an `htmltools::HTML()` value makes knitr print the whole list as code, and HTML inside a string is escaped (`52%<div...` shows literally).
- Put the respondent base into the **title** with `#| title: !expr kpi_title("label", "code")` - `!expr` chunk options work for `title`, so the title is computed from the data while the number stays plain. Use non-breaking spaces (`\u00a0`) in `n = 1 929` or it wraps mid-number.
- Colors: one for "% yes" cards, another for "average" cards. A theme's default value-box text can be unreadable on dark fills (sandstone's was) - `custom.css` forces light text on `.bslib-value-box .value-box-title/.value-box-value`.
- Row height ~190px so a 3-4-line title plus the value fits at 1024 px. Keep titles short; a long one clips.
- Helpers: `kpi_pct(code, yes_options, icon)` (sum of `perc` over chosen `option_orig` values) and `kpi_avg(code, icon)` (mean of numeric `option_orig` weighted by `perc`). **What counts as "yes" is a per-variable decision to confirm with the user** - options like "partially" are not yes by default.

**Chart cards**
- **No `#| title:` on chart cards** - the dynamic `chart_title()` is the title, and a card header with the same text duplicates it. The map keeps its own `.map-title` div.
- `chart_title(text, note = NULL, width = 120)`: `note` adds a smaller second line (used for "Можна обрати кілька варіантів" on any multi-select chart, i.e. shares summing above 100%); **`width` must be ~60 for half-width cards**, since plotly titles can't re-wrap and a 120-char wrap overruns a ~500px card at 1024 px.
- `hbar(..., order = c(<option_orig>...))` lays bars out in a fixed top-to-bottom order (natural/ordinal order); `order = NULL` sorts by value. For any question with an inherent order (grades, tenure, understanding levels) always pass `order`.
- Donut with long category names: percentages on the ring (`texttemplate = "%{percent:.1%}"`, uniform precision) plus a **legend** with the full names on the right (`domain = list(x = c(0, 0.5))` leaves it room), instead of the "label+percent outside" default - three 45-character labels around a small ring get clipped.
- Tooltips on every chart carry the count: `%{x:.0%} (n = %{customdata})`, with `customdata = response_count`.

**Maps in a grid card**
- `leafletOptions(scrollWheelZoom = FALSE, zoomSnap = 0.1, zoomDelta = 0.5)`: with the default integer `zoomSnap` the country sits small in the middle of a wide card; fine zoom steps let the map fill it.
- The overview-map scale was agreed as `"share"` (share of all respondents, count in the tooltip) - ask per dashboard (see "Overview-map scale"). `map_scale()` here implements `"share"` and `"perc"`; `"capped"` is added when a numeric page needs it.
- Natural Earth ships Ukrainian names (`name_uk`): build the geojson `name` from it (strip " область") instead of hand-mapping English names. Two traps: its `name_uk` for the oblast "Kiev" says `Київ` (same as the city) and must be renamed to the survey's `Київська`, and Crimea/Sevastopol come from the Russia subset (see "Maps").

**Data traps found on this page** (check the equivalent on every new dataset)
- A choice label in the aggregated parquet can be wrong while the KoBo form is right (`q_grades`/`none` arrived as the English `"None "`; the form says «Не викладаю»). Compare unfamiliar labels against the KoBo `choices` sheet; `check_sheet.py` flags such labels. **Do not override them in setup** - report them and have the data fixed (this one was fixed at the source: the label now reads «Не викладаю»).
- The option code `n0ne` (with a zero; `q_grades`, `q_admin_support`) is **deliberate**: the user spelled it that way so Python does not read it as a `None` value. Use `n0ne` in order lists; do not "fix" it, and a literal `"none"` silently produces an NA row.
- A multi-select question's own text may already say "Виберіть один або кілька варіантів" (`q_role_understanding`); the chart note then repeats it - accepted, for consistency across multi-select charts.

### Type 2 - Numeric dependent variable with geography
For continuous dependent variables with no discrete options, on the geographic admin dimension.

**Data source**: two tables:
- `agg` - `mean`/`median`/`min`/`max` per (variable, admin, admin_category, disaggregation) combo (`option` is NA). Drives the map and bar chart.
- `agg_num` - the per-distinct-value frequency table for the same variables. Drives the histogram only. Joined and given `response_count` in setup, the same way as `agg`.

**Selectors**: dependent variable | statistic (replaces the option selector) | admin 1/2 | disaggregation variable. No percentages↔counts toggle - the statistic selector supersedes it.
**Graph types**: map, bar chart, distribution (histogram).

**Statistic selector**: a fixed 4-choice picker - Середнє / Медіана / Максимум / Мінімум -> `mean`/`median`/`min`/`max` (`stat_choices` constant, reused as-is). Static `selectInput`, no `renderUI`/`selectize = FALSE` needed. The selected statistic colors the map (`map_scale(..., "capped", digits = 2)`) and sizes the bar chart.

**Bar chart**: no option dimension, so with no disaggregation it's a **single bar** (the selected statistic for the current admin scope), labeled with that scope's name (`bar_scope_label<N>()`: "Уся Україна" / the selected oblast / the selected hromada's name) so the one bar still says what it represents. With a disaggregation selected: **one bar per disaggregation category**, height = the selected statistic. Hand-built with `plot_ly()` + `bar_labels(stat_tickformat)`.

**Distribution tab**: a histogram from `agg_num`, scoped by the same admin/disaggregation filters as the map/bar; always shows the full distribution and ignores the statistic selector. Expand each distinct value into a plain vector (`rep(as.numeric(option_orig), times = response_count)`) and hand it to `plot_ly(x = ~expanded, type = "histogram")` to auto-bin - no manual `cut()`. Skewed variables (e.g. Library `q4_1`: median ~6,577 vs max 1,861,415) would compress into one bar, so trim the vector to values at or below its **95th percentile** first; this drops the top ~5% of respondents from the chart rather than folding them into an overflow bin.

| Selector | changes graph | note |
|---|---|---|
| Dependent variable | all graphs | |
| Statistic | Map graph, bar chart | |
| Administrative category 1 (oblast) | Map graph, bar chart, distribution | Drills down into the hromada map |
| Administrative category 2 (hromada) | Map graph, bar chart, distribution | |
| Disaggregation variable | bar chart (one bar per category); also filters the distribution | |

**Server building blocks**: same `map_drilled<N>`/`bar_scope<N>`/`disagg_active<N>`/`admin1_ui<N>`/`admin2_ui<N>` as Type 1 (no `dv_option_ui<N>`). Additional/different: `bar_scope_label<N>` (reactive); `bar_df_reactive<N>` (reads `input$stat<N>`); `hist_df_reactive<N>` (`agg_num` filtered like `bar_df_reactive<N>`); `map_title<N>`/`bar_title<N>`; `map<N>`/`bar<N>`/`bar<N>_data`; `output$map_title<N>`; `hist<N>` (renderPlotly, titled `hist_title(map_title<N>())`); `raw_data<N>`; `reset<N>` (resets `dv<N>`, `stat<N>` to `"mean"`, `admin1<N>`, `disagg_var<N>`).

### Type 3 - Numeric, no geography, correlation-driven
For continuous scale scores (e.g. 0-1) with no geographic admin dimension. Built from Type 2 (a statistics table plus a distribution table), with the map removed and a correlation matrix, auto-generated findings text and a per-school breakdown added. Developed for the Educ4Life project - its specifics are condensed under "Reference implementation" at the end of this section.

**Selectors**: dependent variable | statistic (same 4 choices as Type 2) | disaggregation variable. **No admin selectors, no map.** All inputs are static choice lists - no `renderUI`/`selectize = FALSE` needed.
**Graph types**: bar chart, histogram, correlation matrix; each paired with a findings-text card. A school-breakdown table replaces the raw-data card.

| Selector | changes | note |
|---|---|---|
| Dependent variable | bar chart, histogram, findings text, school-breakdown table | does **not** change the correlation matrix - that's fixed per page |
| Statistic | bar height, school-breakdown value columns | histogram always shows the full distribution |
| Disaggregation variable | bar chart (one bar per category), findings text | only the participation split (pilot/non-pilot) also changes the correlation matrix; every other choice, or none, leaves it on the single `overall` view |

**Layout**: three tabs, each `### <name> {orientation="rows"}` with `#### Row {height=...}` directly underneath:
- **"Огляд"**: bar chart, histogram, and one shared findings-text card, stacked in that order.
- **"Кореляції"**: the correlation matrix (one or two heatmaps) plus its findings-text card(s).
- **"Школи"**: the school-breakdown table (`DTOutput("school_data<N>")`).

**Bar chart**: same shape as Type 2's, from the stats table at `admin == "Overall"`. The single undisaggregated bar's label is the whole sample ("Загалом" or similar) - not "Уся Україна", since there's no national/oblast framing.

**Histogram**: as Type 2's (`rep()` expansion, auto-bin; `response_count = perc * general_count`). If the distribution table only has `admin == "Overall"` rows (Educ4Life's does), the histogram is always the full-sample shape, unaffected by disaggregation.

**Findings-text cards**: auto-generated Ukrainian text, one row per sentence, in a findings table (`visual_id`, `order`, `text`). Build the lookup key exactly to its fixed grammar - don't re-derive it:
- Bar + histogram (one shared card for both - the facts combine level and shape sentences in one block): `hist|<variable_orig>|<disaggregation short code or "Overall">|Overall`.
- Square result-group matrix: `corr|result_groups|<group>`.
- Rectangular page matrix: `corr|performance|<page_key>|<group>`.
- `<group>` is `overall`/`pilot`/`non_pilot` (subset pages prefix these with `clean_`, and use `hist_clean|...`).
- Render matching rows' `text`, ordered by `order`, as a paragraph/bullet list. Zero rows is legitimate (e.g. the analyst hid every sentence) -> render a placeholder ("Немає автоматичних спостережень для цього вибору"), never an error.

**Correlation matrix** - a stable pattern, reuse as-is. Two views, from a precomputed Spearman correlations table (`set`, `group`, `var1`, `var2`, `rho`, `p_adj`, `order1`/`order2`):
- **The page whose own variables are the top-level "result group" set** gets a **square heatmap** of that set against itself (`build_corr_heatmap(group_name)`), ordered by the precomputed `order1`/`order2` hierarchical-clustering columns - similar variables end up adjacent, so the axis order itself is informative.
- **Every other page** gets a **rectangular, page-scoped heatmap** (`build_page_corr_heatmap(page_key, group_name)`): the page's own variables as rows; every *other* page's variables plus fixed context covariates as columns. Rows and columns never overlap, and result-group variables never appear here. Deliberately not one everything-vs-everything matrix: a full N×N matrix is unreadable, and the useful per-page question is "how does my page's performance relate to every other page's, plus the context covariates". Both axes keep their declared order, not cluster order.
  - `page_vars` (named list: page key -> its variables) is the single source of truth for both axes. It's duplicated in the findings pipeline and the dashboard setup chunk - keep both in sync. A page can be in `page_vars` (so its variables appear as columns elsewhere) without having a matrix of its own.
  - Column labels must stay short (up to ~18 columns on one axis); a project-specific `axis_label(var)` maps each variable to a short label rather than the full question text.
  - Data: the rectangular view uses the `performance` set (every non-result-group, non-context score crossed with itself) for rows × other-page columns, plus `context` pairs for the context columns; the square view uses the `result_groups` set. A narrower "blocks only" set was tried and rejected: it never produces the cross-subject pairs a page-scoped view needs.
  - Composite scores (e.g. a STEM score that sums subjects) correlated against their own components are included, by explicit decision - expect very strong (~0.85-0.90) correlations there; that's expected, not a bug. Keep composites out of any ranking that assumes non-overlapping members.
- **Disaggregation state**: participation split selected -> **two** heatmaps (`pilot`, `non_pilot`); anything else -> **one** (`overall`). **Stack the two vertically**, not side by side - a rectangular matrix with up to 18 column labels is unreadable at half width. Because the number of heatmaps changes, the container is a `uiOutput`/`renderUI`, not a fixed `plotlyOutput`.
- Color scale: see "Shared chart helpers".

**Correlation findings text**: generated per page × group, up to four fact types per card: `corr_top` (strongest pairs), `corr_context` (strongest relation to a context covariate), `corr_isolated` (a page variable with no notable correlation), `corr_group_diff` (a pilot-vs-non-pilot difference in the same pair, via a Fisher's z-test). Two different significance tests, don't conflate them: individual pairs use Spearman `cor.test(..., method = "spearman", exact = FALSE)` with Benjamini-Hochberg `p.adjust(..., "BH")`; the group difference uses Fisher's z. `corr_group_diff` facts almost never reach the dashboard - their priority (2.5) loses the top-3 slot to `corr_structure` (1) and `corr_top` (2.1-2.3) on the same card. To surface them, change priorities or give them a dedicated card.

**School-breakdown table** (raw-data replacement - optional and project-specific; verify it fits before reusing). Built from the stats table's `admin == "school_id"` rows, pivoted so each school is one row with pilot/non-pilot side by side (a school missing one group shows NA on that side, not a missing row):

| school_id | school label | `<statistic>` (Учасник) | n (Учасник) | `<statistic>` (Неучасник) | n (Неучасник) |
|---|---|---|---|---|---|

Uses the selected `stat<N>` (so it matches the bar chart) but is **not** filtered by the disaggregation selector - it's always split by participation, the only split the school rows have. Follows the raw-data DT convention (`pageLength = 25`, `filter = "top"`, `bPaginate = TRUE`, buttons), always reactive. Gotchas hit while building it - re-check each if reusing:
- The `colnames` length gotcha (see DT gotchas) - this table's hidden `significant` column triggered it.
- **Compute per-school significance live; verify any upstream significance column first.** Educ4Life's TOC file looked like it held per-school p-values but held one per *variable*, and a per-school-looking list repeated the same number - an upstream formatting artifact. The fix: a small live ANOVA per school (`aov(x ~ factor(participation))`), gated by the pipeline's own `school_min_n`/`alpha` thresholds, cross-checked against the aggregate-level fact.
- **A "how many schools are higher/lower" sentence must count only the significant rows**, and the counts should be validated against the table (higher + lower + equal == significant count).
- A school-name lookup file is optional and project-specific; confirm it exists and that its id format matches the data's before joining.

**Subset pages** (optional): a page can show the same Type 3 shape for a sub-population (Educ4Life: respondents without signs of academic dishonesty). The DAF gets a second full copy of the relevant variables' analyses at a fixed `ID` block, with the **same `variable_orig` names**, so: exclude that ID block from the regular `agg`/`agg_num` immediately after loading (before dedup), build `_clean` counterparts (`agg_clean`, `agg_num_clean`, respondent data filtered to the subset) once in setup, and point the subset pages' reactives at those. ### Type 5 - Grid of variables with a breakdown selector (static, OJS)
A page that shows **all** of its variables at once as a grid of cards, with a small sidebar of selectors that applies to every card (no variable picker). Built for the static GitHub-Pages variant (see "Architecture"); first used on Supervision Page 1. Two variants share all the page mechanics: the **standard** variant (one respondent population - the card recipes in the table below) and the **two-group comparison** variant (every table split by respondent group - see "Variant: two-group comparison" further down, used on Supervision Page 5). Everything outside the card recipes and the data shape applies to both.

**Selectors (sidebar)**: **breakdown** (`Загалом` = Overall, plus the project's disaggregation variables, e.g. oblast, years of experience) | **percentages / counts** radio | **Скинути** (reset) button. Nothing else: no variable, option or admin selectors.

**Chart type depends on (question kind × breakdown)** - the whole point of the type. The classification sheet carries it per variable (`Page_gen_type_graph` = overall view, `Page_graph_disag_chosen` = breakdown view, both from a controlled vocabulary - see "The classification sheet" in Part 2); the standard variant's recipe is:

| Question kind | Overall | With a breakdown |
|---|---|---|
| single choice | donut | 100% horizontal stacked bar, one bar per category (bar length = n respondents in counts mode) |
| multi-select (shares sum > 100%) | sorted horizontal bar, with the "Можна обрати кілька варіантів" note | **heatmap** (categories x options, colour = share/count; stacked bars are invalid here) |

- **Option order is fixed per variable** (`p1_order` in R: ordinal answers most- to least-positive; multi-select by overall share, "did not receive" last), colours come from a sequential brown ramp by position in that order (3 or 4 steps), white separators between segments.
- **Small groups are dropped, not shown**: disaggregation categories with fewer than `min_n` (30) respondents are removed in R before export, and each card says how many ("Не показано 8 з 25 областей: менше ніж 30 респондентів."). If a breakdown leaves nothing, the card shows a short "Недостатньо даних" placeholder. The `Overall` view is never filtered. This also covers disclosure risk on a public site.
- **A breakdown that is degenerate for a question** (e.g. a question asked only of teachers, split by position) should not be offered at all - strip it from the data/dropdown rather than showing one-bar charts.
- **Zero-fill in R before export**: the pipeline omits options nobody chose in a category, so complete every (variable, category) x option grid with `perc = 0`; the browser code then never has to handle missing cells.
- **Y-axis labels that look like numbers** (years) must be forced with `type: "category"` on every categorical axis, otherwise Plotly treats "2019" as numeric and the bars fall outside a 0..N axis.
- **Counts** = `round(perc * general_count)`, computed in R and shipped as a column; percent/count is just which column the chart reads (`key = valtype`), with the d3 format (`.0%` / `,d`) switched alongside. Every tooltip shows both the share and `n`.
- **Layout hints from the sheet** (`Layout_hint`): `auto` (default), `full_row` (the card always takes the whole row) or `new_row` (the card starts a new row; a lone previous card then fills its own row). The category order of a breakdown, its Ukrainian label/wording and the small-group threshold (`min_n`) also come from the sheet (`breakdowns`, `main`), not from the code.
- **Layout - a hand-rolled auto-height grid**, not Quarto Rows (their pixel heights can't follow a chart that needs 700 px for 25 bars): `## Row {.flow}` containing one OJS cell that returns `<div class="p1-grid">` (CSS grid, `repeat(auto-fit, minmax(420px, 1fr))`, styled in `custom.css`). Each card's plot height is computed from its category/option count (~30 px per bar + ~150 px). Cards with more than 8 categories, and every heatmap, get `.wide` (full row). Compact cards (donuts, few-bar charts) sit two per row.
- **Cards that share a row must share a plot height**: stacked-bar cards for questions with fewer categories (e.g. a leaders-only question with 2 experience groups next to 4-group questions) otherwise end earlier and their axes don't line up. All compact (<= 8 categories) stacked cards use the tallest card's slot count, with the y axis given a fixed `range: [slots - 0.5, -0.5]` so bars keep the same thickness and the empty space sits under them. Cards with many categories (`.wide`) keep their own height.
- **No blank half-rows**: the grid is 2 columns when its container is >= 880 px wide, otherwise 1 (set in JS, not by CSS `auto-fit`, so the layout can be reasoned about). `layoutGrid()` walks the cards in order; a card that would be alone in its row (the last card, or the one right before a full-width `.wide` card) gets `grid-column: 1 / -1` and fills the row. It runs before the first draw and again from the `ResizeObserver` (sidebar open/close, window resize), which then calls `Plotly.Plots.resize`.
- **Vertical bars that fill their row**: a card can be drawn as columns instead of horizontal bars (`vertical` in the config; set in R: standard variant `vertical = code == "q_form"`, comparison variant `h_experience` and `h_informed`). The point is to use the space of a row whose neighbour is tall: such a part is marked `fill: true` and its `build(slots, fillH)` returns `height = max(natural height, fillH)`. `mountGrid` first measures the tallest *non-fill* card of each row, then passes that as `fillH`, so a column chart next to a tall bar chart grows to the same height instead of leaving a gap. `slots = 0` for these cards (they don't take part in the shared-axis logic). Use `tickangle: 0` and wrap category labels at ~14 characters; put the legend **above** the plot (`y: 1.01, yanchor: "bottom"`, top margin +26 px) - a side legend squeezes the columns until their labels rotate, a bottom legend collides with the labels.
- **Subtitle on every chart**: a second, smaller title line "Відповіли N" - N is the question's total respondents (its `Overall` base), the same in every breakdown view, so it stays comparable even though small groups are dropped from the chart. On multi-select charts it shares the line with the note: "Відповіли 1 929 · Можна обрати кілька варіантів". Page 0 does the same via `answered_note(code, extra)` in R. The top margin is **one value per page** (`topPx`, from the longest title + subtitle at half width) so cards in a row keep aligned axes; a fixed 70 px margin let a 3-line title collide with the first bar label.
- **Titles**: `chart_title()` ported to JS (`titleOf`); the breakdown is appended in brackets ("... (за областями)"); `width` ~60 for half-width cards, ~120 for `.wide` ones. No `#| title:` on the cards.

**Card kinds** (`kind` in `renderPage()`; chosen from the sheet's two chart-type columns, the question's KoBo type and the breakdown):
- `kpi` - overall view of a 1-5 rating question ("card with the average number"): teal card with the mean as "4.3 / 5" and "відповіли N" (mean = sum of option x share). Compact, sits two per row.
- `donut` / `bar` - overall view of a single-choice / multi-select question.
- `stack` / `heat` - the breakdown view of those two.
- `mean` - breakdown view of a rating question ("bar chart" in the sheet): one bar per category = its mean score on a fixed 0-5 axis, n in the label. Not affected by the percent/count switch.
- `empty` - the breakdown leaves **fewer than 2** categories after the n<30 rule: the card shows "Недостатньо даних для порівняння: менше двох областей мають щонайменше 30 респондентів." instead of a one-bar chart (the "Не показано N з M" note still appears). This is common on low-base questions (e.g. only 1 oblast of 23 reaches 30 respondents on questions asked of the 241 participants).
- **Multi-select comes from the KoBo form** (`select_multiple` in the survey sheet of the questionnaire), not from guessing at the shares; the "Можна обрати кілька варіантів" note appears only on those. A script check refuses a donut for a multi-select question.
- **Option labels**: the pipeline stores numeric answers as "1.0"; R strips the ".0". Numeric answers are ordered ascending, other answers by `p_order` (ordinal, most to least positive) or by overall share; "Інше", "Важко відповісти"/"Не знаю" and "did not receive" always go last and are grey (`#b9c4d0`). Colours are assigned in R (ramps of 2-5 blues over the non-neutral options) and shipped as a `color` column; text colour on a segment is picked from its luminance.
- **Row alignment generalised**: `layoutGrid()` groups the cards into rows, and cards of the bar-like kinds (`bar`, `stack`, `mean`) in one row share a `slots` count (bars per plot); the y axis gets a fixed `range: [slots - 0.5, -0.5]` so bars keep their thickness and the empty space sits below. A stacked card also reserves enough slots for its wrapped legend (otherwise the legend scrolls), and the overall bar charts use a page-wide pixel height per bar derived from the longest wrapped label (4-line labels overlapped at 34 px). Heatmaps size their top margin from the title lines + wrapped column labels, and wrap labels at 11 characters when there are more than 8 columns.

**Implementation recipe (all in `index.qmd`) - one shared implementation for every Type 5 page**
1. **One R chunk for all pages** (`#| include: false`, in the first Type 5 page's sidebar): read the classification workbook (`survey`, `main`, `breakdowns`, `lists` sheets) and the KoBo form (multi-select), validate every controlled column against the `lists` sheet and **stop the build with a plain message** on a word outside the vocabulary or a missing/duplicate `Card_order`, then build the flat data frames and ship them with `ojs_define()`: `pg_cfg` (page, pos, code, label, multi, overall, disag, keep_order, vertical, layout_hint), `pg_opts` (code, option_orig, option, rank, color), `pg_rows` (variable, admin, category, option, rank, perc, count, base; zero-filled, categories under the page's `min_n` removed), `pg_dropped`, `pg_bk` (the `breakdowns` sheet) and `pg_spec` (the `main` sheet: breakdown choices, value toggle, threshold). **Flat data frames only** (nested lists get unboxed unpredictably). Card order is the sheet's `Card_order` - nothing is inferred any more.
2. **One shared grid kit** (`gridKit`, an OJS cell used by both variants): `wrap`, `titleOf`, `baseLayout`, `isLight` and `mountGrid(cards, invalidation)`, which owns the CSS grid, the row-filling layout, the shared `slots`, the `Plotly.react` redraw and the `ResizeObserver`. A card handed to `mountGrid` is `{el, wide, slots, parts: [{plot, build(slots) -> {traces, layout, height}}]}` (several `parts` = several plots in one card, e.g. two heatmaps). A new variant only has to build its cards.
3. **One OJS definitions cell** (`//| output: false`): `transpose()` the frames, `Plotly = require("plotly.js-dist-min@2.35.2")` (pinned, loaded from the CDN - the page needs internet), the sidebar control factories `breakdownSelect(page)` and `valueRadio(page)` (their choices and the existence of the percent/count toggle come from the page's row in the `main` sheet, labels from `breakdowns`), `resetButton(disagInput, valueInput)` and `renderPage(page, disag, valtype, invalidation)`. **Pass `invalidation` into the function** - inside a function defined in another cell it would refer to that cell, not the caller.
4. **Per page**: a `## {.sidebar}` with three OJS cells (`viewof disagN = breakdownSelect(N)`, `viewof valtypeN = valueRadio(N)`, `viewof resetN = resetButton(viewof disagN, viewof valtypeN)`), then `## Row {.flow}` with `gridN = renderPage(N, disagN, valtypeN, invalidation)`. A new page = a row in `main`, rows in `survey` (with `pages`, `Card_order`, chart columns), a new heading + these cells + a `NAV_ICONS` entry; everything else comes from the sheet. `check_sheet.py` verifies that the page titles, icons and headings agree.
5. **Inside `renderPage`**: build every card (`makeCard`) and `return mountGrid(cards, invalidation)`. `mountGrid` draws only once the grid is attached (`requestAnimationFrame` loop on `root.isConnected` - Plotly measures its container, a detached node gets the default 700 px) and redraws from a `ResizeObserver` when the grid's width changes (Plotly's `responsive` only reacts to window resizes, not to the sidebar opening).

**Variant: two-group comparison (`renderComparePage`; Supervision Page 5)**
For questions that were asked of **two respondent groups** (Supervision: Керівники та заступники vs Вчителі) and harmonised into one set of variables, with **every frequency table split by the group** (`disaggregations_category_1_orig` = `manager`/`teacher`; `admin` = Overall / the project's breakdowns). It is the same page type: same sidebar (breakdown, percent/count, reset), same `gridKit`/`mountGrid` (grid, row filling, shared slots, fill-the-row columns, resize handling), same n<30 idea, subtitles, notes and static/dynamic cards. Only two things change:
- **the data has one more axis** - a card is chosen by (question kind x breakdown x group) instead of (question kind x breakdown), and rows are keyed by (category, group, option);
- **the card recipes** (table below), plus the rules that follow from the second group (not-asked options, per-cell small-group rule, two bases).
It has its own data chunk (`cmp_*` frames) and its own render function because those two things differ; everything that is not a card recipe is shared. The classification sheet's **`Graph_type`** says which cards react to the breakdown dropdown: `static` cards ignore it (and, with `Hidden_when_breakdown = yes`, are hidden once a breakdown is chosen), `dynamic` ones follow it (a `static, dynamic` question is a static card on page 0 and a dynamic one on its page).
*Known gap:* the comparison variant takes page membership, `Card_order`, `Orientation_overall`, `Layout_hint`, `Graph_type` and `Hidden_when_breakdown` from the sheet, but its card **kinds** are decided in the R chunk (`cmp_cfg`) from the KoBo type; the sheet's chart wording is checked against what the page can draw (the build stops if it asks for something else), so the two cannot drift silently.

| Card | Kind | Overall view | With a breakdown |
|---|---|---|---|
| the groups themselves | `pop` (static) | donut of the two groups | same (ignores the dropdown) |
| composition of the sample by oblast / experience | `comp` (static) | 100% stacked bar per category: share of each group among that category's respondents (counts mode: stacked counts) | same |
| single-choice question | `single` (dynamic) | one 100% stacked bar per group (2 bars), answers as segments | **two heatmaps**, managers above teachers, same colour scale |
| multi-select question | `multi` (dynamic) | **grouped** bars (a pair per option, not stacked - shares sum above 100 %) | two heatmaps |

Rules that are specific to this kind of page:
- **Labels come from the harmonised KoBo form**, not from the parquet (whose option and category labels are English): `choices` -> `label::Ukrainian`, matched on the code. Decode HTML entities first (see the gotcha). Question texts in the parquet are already Ukrainian.
- **"Not asked" is not 0 %.** The KoBo `choices` sheet's `available_to` (`both` / `teachers_only` / `managers_only`) says which group saw an option. Zero-fill only the options a group was asked; the rest stay absent, and the browser draws no bar / a blank cell. Grouped-bar labels carry "(лише вчителям)" / "(лише керівникам)"; in the heatmaps the columns are ordered "asked of both | managers only | teachers only", so the blank blocks are legible.
- **Small groups, per cell**: a breakdown category is kept if **at least one** group has 30 respondents; the other group's cells are blanked ("порожні клітинки" note under the card), and categories where neither group reaches 30 are dropped with a "Не показано N з M" note. The static composition cards drop categories with fewer than 30 respondents in total.
- **Subtitle with two bases**: «Відповіли: керівники 466 · вчителі 1 929» (+ the multi-select note). The groups can differ in what they answered about (teachers about themselves, managers about their staff) or in base (barriers: teachers who did not take part vs all managers) - a hand-written one-line note under such cards says so (`cmp_notes` in the R chunk; confirm wording with the user).
- **Empty rows/columns are removed from each heatmap separately** (a row/column with no value at all for that group: not asked, or under 30 respondents), so the two heatmaps can have different rows and columns. A subtitle line under the chart title (first heatmap) or above the second heatmap says what was left out: «Керівники: не показано 14 з 17 рядків і 4 з 13 стовпців через відсутність даних для цієї категорії». Cells that are blank inside a kept row/column are explained by the note under the card. A group with nothing at all shows «Немає даних для цієї групи». (The standard variant's heatmaps are zero-filled, so they never have empty rows or columns.)
- **Static cards are hidden under a breakdown**: with a breakdown chosen, the `Graph_type == static` cards (`h_population`, `h_experience`, `h_oblast`) are removed from the grid (`c.static` in `cmp_cfg`), so the page starts directly with the comparisons; they only show in the overall view.
- Group colours are fixed everywhere: managers navy `#143a6b`, teachers mid-blue `#6fa5d8`.
- Card order is set in R (`cmp_cfg`): the two small composition cards first, then the oblast composition (full row), then the comparisons in sheet order.

**Gotchas (static / OJS)**
- **`Inputs.select` with a `Map` uses the option *index* as the DOM `value`**, not the Map value: when driving it from a test or script set `select.selectedIndex`, not `select.value`. Likewise trigger a radio with a real `.click()`; a synthetic `checked = true` + `input` event does not update it.
- **bslib sidebars on a non-initial page come up collapsed**: they're built while their tab is hidden (zero width), and the collapse happens at an unpredictable moment after load. `nav-icons.html` re-opens each visible collapsed sidebar (a short poll after load + on every `shown.bs.tab`) until the user collapses it themselves (a *trusted* click on its toggle).
- **Don't hard-code the spelling of the Overall category in JS** (`" Overall"` with a leading space in some pipelines): take the single category present in the filtered `admin == "Overall"` rows.
- **Use a fixed system font stack in OJS Plotly layouts** (`font.family = "Arial, Helvetica, sans-serif"`), not `"inherit"`: Plotly measures label/legend text and **caches the widths**; if the theme's web font loads afterwards, the wider glyphs overflow the cached widths and legends/axis labels are clipped (a redraw after `document.fonts.ready` does *not* help, the cache survives). Hit when switching sandstone -> cosmo.
- **Observable `Inputs.button` isn't styled by the theme** (and its own stylesheet beats a plain class): give the inner `<button>` a class (`form.querySelector("button").classList.add("p1-reset")`) and style it with `!important` in `custom.css`. Don't select sidebar `button`s generically - the collapse toggle and other widgets are buttons too.
- **Plotly label clipping**: `automargin` alone isn't enough for long category labels - set explicit left/right margins (~185 px left for "Івано-Франківська (n = 97)", ~190 px right when a vertical legend sits beside stacked bars), wrap donut legend entries at ~14-16 characters, and set `legend.traceorder = "normal"` (stacked horizontal bars reverse the legend by default). In counts mode hide segment labels on segments that are tiny relative to the longest bar, and pin `textangle: 0`; narrow segments otherwise get rotated labels.
- **`openxlsx::read.xlsx()` can return non-ASCII text entity-encoded** (`&#1044;&#1086;...` for "До"; seen on the harmonised KoBo file, not on the others). Plotly still renders it correctly, so it goes unnoticed until you sort or compare by label (an order list never matches) or wrap by length (the entities are counted, so labels break into one word per line). Decode in R right after reading (`decode_entities()` in the page-5 chunk) and compare with a browser console check of `plot.data[0].y`.
- **Heatmap in a half-width card**: Plotly rotates the x tick labels vertically and they collide with the title - make heatmaps `.wide` and set `tickangle: 0`.
- **Screenshot harness**: a full-page capture (`captureBeyondViewport`) temporarily changes the viewport, which makes bslib collapse the sidebar and never re-open it. For tall pages grow only the viewport *height* via `Emulation.setDeviceMetricsOverride` before `Page.captureScreenshot`. A static `index.html` can be served with `python -m http.server` (bind 127.0.0.1) and stopped afterwards by the PID listening on its port.

## Deployment (shinyapps.io) - generic rules
Read before deploying or changing any runtime file path. Project-specific targets and data policy are in Part 2.
- **No runtime use of rnaturalearth.** Overview maps read the cached `data/oblast_geo.geojson`. The local `rnaturalearth` is a GitHub dev build (1.2.0.9000) and `rnaturalearthhires` isn't on CRAN - either one in `library()` makes the shinyapps.io build fail. rsconnect detects packages by scanning code, so check with `renv::dependencies("index.qmd")`; mentions inside comments are ignored.
- **Memory is the main deployment risk.** shinyapps.io's default instance (`large`) has only **1 GB** ([instance sizes](https://docs.posit.co/shinyapps.io/guide/applications/): small 256 MB, medium 512 MB, large 1 GB, xlarge 2 GB, xxlarge 4 GB, xxxlarge 8 GB; the larger sizes need a paid plan). Going over it looks like `The application failed to start. signal: killed` and, later, `Container event ...: oom (out of memory)` in the logs - with no R error. (Check the app's size with `rsconnect::applications(account)$size`.) The Library dashboard hit this twice; measured on the first failed deploy, startup peaked at **3.1 GB** and holding the data cost ~0.9 GB of R heap. Now: **~0.63 GB process peak, ~0.3 GB R heap, 6 s startup.** What got it there - keep all of these when changing the setup chunk:
  - **Never `read_parquet()` a whole big file.** Read only the columns the app uses (`agg_cols`/`agg_num_cols`; add a column there when a page starts using it) via `read_parquet_cols()`: **one column at a time, text columns as dictionaries**. Arrow materializes every row's string separately (R shares identical ones), so a long repeated column like `title` (56k distinct values over 3.7M rows) alone peaked at ~2.4 GB.
  - **Keep rarely-used rows on disk.** Hromada-level rows split by a disaggregation were 71% of `agg` but are needed only when a user picks a hromada *and* a disaggregation. `data/prepare_runtime_data.R` writes `dash_input2_main.parquet` (held in R) and `dash_input2_hd.parquet` (queried on demand with `read_hd(hd_agg, variable_code, hromada_code, disagg_code)`, ~30-60 ms per call); the same split exists for `agg_num` (`hd_num`). Every page's `bar_df_reactive<N>` (and the histogram reactive on pages that disaggregate it) takes the `read_hd()` branch when `disagg_active<N>() && bar_scope<N>() == "hromadaId"`. **Any new reader of hromada-level data must either use only the non-disaggregated rows (`disaggregations_1_orig == " Overall"`, in memory) or go through `read_hd()`** - the in-memory `agg` has no hromada x disaggregation rows. (Verified: every (variable, hromada, option) present in the disaggregated rows also exists in the non-disaggregated rows, so dropdowns and maps are unaffected.)
  - **Don't parse xlsx at startup.** `readxl` needs ~500 MB just to read the 6 MB respondent file. The app reads `data/clean_readable.parquet` (identical data, converted by the same prep script).
  - **No `left_join()` on the big tables** (it copies the whole table) - `add_admin_2()` adds columns in place with `match()`. **No per-call `agg %>% filter(...)` just to look something up** (`get_label()` is a lookup built once).
  - **Re-measure after touching setup**: evaluate the setup chunk statement by statement and record the process's `PeakWorkingSet64` and `gc()` max-used after each. Aim to stay well under half the instance size - per-session reactives add transient copies, and Linux (shinyapps.io) doesn't return freed memory as eagerly as the Windows numbers above.
- **Every file the app reads must be in the bundle**, read with paths relative to the app directory (no `here::here()`/`here::i_am()`).
- **Deploy with rsconnect, not the Quarto CLI.** Quarto 1.10 has no `shinyapps` publish provider (`quarto publish shinyapps` fails with "Publishing source 'shinyapps' not found"). Use `rsconnect::deployApp(appDir = ..., appPrimaryDoc = "index.qmd", appName = ..., account = ..., metadata = list(quarto_version = ..., quarto_engines = list("knitr")))`.
- **Why the `metadata` argument is needed:** on Windows with the Ukrainian ANSI codepage, rsconnect's own `quarto inspect` call receives the dashboard's UTF-8 Cyrillic output garbled, and it fails in `sanitizeSystem2json()` ("invalid UTF-8" or "invalid character inside string") in both rsconnect 1.5.0 and 1.11.2. Supplying `quarto_version` and `quarto_engines` makes rsconnect skip that call. `quarto_engines` must be a list, not a string - a string fails manifest schema validation.
- **Deploy command and app layout**: the app lives in a `dashboard/` subfolder (`appDir = "dashboard"`), runtime data is copied into `dashboard/data/` by a sync script (Educ4Life: `scripts/04_sync_dashboard_data.sh`, which also rebuilds `oblast_geo.geojson`), and the deploy command is run inline with `quarto_version` hardcoded (currently `"1.10.18"` - update it when Quarto is upgraded). With this layout, render with `quarto render dashboard/index.qmd`.
- **`upload = FALSE` is ignored by rsconnect 1.11.2** - it creates the content record on the server and tries to deploy. Don't use it as a dry run. To see what would be uploaded without deploying, use `rsconnect::listDeploymentFiles(appDir)`.
- **Render before every deploy.** shinyapps.io does not pre-render Shiny Quarto documents, so the bundle must contain `index.html`; without it the app crashes at startup ("Prerendered HTML file not found"). Run `quarto render index.qmd` first. `.rscignore` must never exclude `index.html`. With `embed-resources: true` in `_quarto.yml`, `index_files/` isn't needed.
- **Bundle exclusions** (`.rscignore`): at minimum `index.knit.md`, `index_files/`, `.quarto/`, `.Rhistory`, `.Rproj.user/`, `rsconnect/`, plus docs, pipeline scripts and any respondent-level file the app doesn't read. **`.rscignore` matching**: rsconnect 1.5.0 matched only plain names, per folder - no paths (`data/x.csv`), no wildcards (`*.xlsx`) - so each subfolder needs its own `.rscignore`. The per-folder setup also works under 1.11.2; whatever the version, verify with `listDeploymentFiles()`.
- **Git ignores** `index.html`, `rsconnect/` and the data folder's *data* (`/data/*`), but not its code and deploy config: `data/*.R` (the pipeline scripts, incl. `prepare_runtime_data.R`) and `data/.rscignore` are versioned, via `!` exceptions in `.gitignore`. Anything a script or the app needs that git ignores must be rebuilt or supplied locally on a fresh clone.
- **Failed deploys leave content records on the account**, some with a partial bundle. Delete them in the shinyapps.io dashboard; rsconnect doesn't clean them up.
